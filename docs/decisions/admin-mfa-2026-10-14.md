# Design decisions — administrator MFA (TOTP), 2026-10-14

Administrators are the only password principals in the system (members sign in
with an OTP, section 6), so they are the one account type for which a second
factor is meaningful. This records how MFA is built, not just that it exists.

## Decisions

- **Second factor is TOTP (RFC 6238)** — SHA-1, 6 digits, 30-second step, ±1 step
  of clock-skew tolerance. That is what Google Authenticator, Authy and 1Password
  emit by default, so no client work is needed to get a working authenticator. It
  is implemented against `node:crypto` rather than a dependency, consistent with
  the scrypt decision in `common/crypto/password.ts` — no native module to break a
  Windows dev box and an Alpine container differently.

- **Enrollment is opt-in and self-service, and only persists a proven secret.** The
  pending secret is carried back to the client in a signed, short-lived
  (`typ: mfa_enroll`, 10 min) token, and is written to `AdminUser.mfaSecret` only
  after the client submits a code that matches it. Two consequences: no schema
  change (the `mfaSecret` column that already existed is the whole storage story),
  and there is no such thing as a half-enrolled row — a secret in the database
  always means a working second factor.

- **A correct password is not a session when MFA is on.** `POST /admin/auth/login`
  answers with `{ mfa_required: true, challenge_token }` (a signed
  `typ: mfa_challenge` token, 5 min) instead of the token pair, and the pair is
  only issued by `POST /admin/auth/mfa/verify` with a current code. A wrong code
  is counted by the same lockout as a wrong password, so the brute-force ceiling is
  5 tries either way rather than 5 per stage.

- **The secret is encrypted at rest** with AES-256-GCM under a dedicated
  `MFA_ENCRYPTION_KEY`, stored as `v1.<iv>.<tag>.<ciphertext>`. This mirrors the
  `OTP_HASH_SECRET` reasoning: a secret that protects authentication should not be
  recoverable from a database dump alone, and it should be rotatable independently
  of the JWT keys. Rotating the key makes existing secrets unreadable, which is the
  correct failure mode — affected administrators re-enroll, and no one signs in with
  a factor the server can no longer verify.

- **Recovery is an audited admin action, not a support script.** An administrator
  holding `admin:manage` can clear another administrator's MFA with
  `POST /admin/admins/:id/mfa/reset`, which writes an `AuditLog` row. Clearing the
  factor does not grant access on its own — the account still needs its password —
  so this is a lockout-recovery path, not an impersonation path. Backup codes were
  considered and deferred; the residual gap is a sole Super Admin who loses their
  device with no other `admin:manage` holder, which needs database access to undo.

- **Token separation is by `typ`, as everywhere else.** Enrollment and challenge
  tokens carry their own `typ` values and the admin access token carries
  `admin_access`, so none of the three can be replayed as another. A challenge token
  in particular is not a session: it is accepted by exactly one endpoint.

- **`mfa_enabled` is surfaced on `AdminUserView`** so the dashboard can show an
  administrator's state. The secret itself never leaves the server after activation.

## Interaction with existing decisions

- **Complementary to section 6/24.** Members authenticate by OTP; administrators
  by password plus TOTP. MFA closes the gap that the admin password is a single
  reusable secret, without changing the member flow.
- **Audited like every other sensitive admin action (section 32).** Enabling,
  disabling and resetting MFA all write to the append-only `AuditLog` through
  `AuditService`.
- **No schema migration.** The change uses `AdminUser.mfaSecret`, which the initial
  migration already created, and adds no table.
