# Client decision — SMS provider is MSG91, received 2026-10-14

Resolves **GAP-12** (SMS provider undecided) from
`client-provider-decisions-2026-10-01.md`. The client supplied an MSG91 account and
confirmed MSG91 as the transactional SMS provider for one-time codes. This is the
authority for how OTPs are delivered; it does not change the email provider, which
remains open.

## Decision

- **Provider: MSG91.** OTPs are delivered through MSG91's **Flow API**
  (`POST https://control.msg91.com/api/v5/flow/`), authenticated with the account
  **authkey**.
- **SMS stays OTP-only.** The client's earlier answer G1 keeps SMS to one-time codes
  and nothing else, as a cost saving. The delivery seam reflects that: its only
  operation is `sendOtp`.
- **DLT registration remains the client's to complete.** It is required for
  transactional SMS in India regardless of provider.

## Why the Flow API and not MSG91's OTP API

MSG91 also offers a SendOTP API that generates and verifies the code itself. Using it
would move verification into the vendor while the platform already owns OTP state: codes
are hashed under `OTP_HASH_SECRET`, attempt-counted, and expired against `OtpRequest`,
and the delete-account flow consumes a code at a later step. Two sources of truth for
"is this code valid" is the exact ambiguity the OTP module was written to avoid, so the
code travels as a Flow template variable and MSG91 only delivers it.

## Effect on the build

- `SmsGateway` (abstract) with `Msg91SmsGateway` implementation and a small
  `SmsModule`, bound like `PaymentGateway`/`RazorpayPaymentGateway` so tests can
  substitute a gateway without the network.- `AuthController.requestOtp` sends via the gateway. **Outside production**, when
  the gateway is unconfigured, the response echoes `dev_code` so the flow is testable
  without an account. **In production**, an unconfigured gateway fails closed with
  `401` rather than answering success for a code that was never sent.
- The gateway **reads the balance before sending, and reports it instead of acting
  on it** (2026-10-30, corrected 2026-10-31). MSG91 accepts a Flow request, answers
  `type: "success"` with a request id, and can drop the message afterwards, so the
  reading looked like the only warning available and an earlier version refused the
  send on a zero. It no longer does: the legacy balance endpoint reported `0` on
  every route for an account whose dashboard showed a funded balance, and MSG91 does
  not document a general wallet-balance API at all. A false zero would have locked
  every user out of signing in — worse than the silence it was meant to prevent — so
  a zero now logs an error, flags `reportedZeroBalance` to the caller, and the send
  continues. The reading is cached for a minute, so a burst of logins costs one probe
  rather than one per code.
- A **failed send is now named**, so the app can say something useful (2026-10-31).
  Production answers `503` with `code: "SMS_UNAVAILABLE"` and copy written for a user
  ("we could not text your code just now") — the vendor diagnostic stays in the log,
  where an operator can act on it. One code covers every cause, because the user's
  situation is the same in all of them. In development the code is still echoed as
  `dev_code`, but alongside a `delivery_warning` whenever the message did not go out
  or the balance looks doubtful; that blind spot is what kept a broken send path
  invisible.

- New configuration: `SMS_TEMPLATE_ID` (the MSG91 template id, distinct from the DLT
  template id), `SMS_OTP_TEMPLATE_VAR` (the template variable that holds the code,
  default `OTP`), and `SMS_COUNTRY_CODE` (default `91`). `SMS_PROVIDER_API_KEY` holds
  the authkey; `SMS_DLT_*` stay for compliance.

## Open / follow-ups

- **Rotate the authkey.** The key was shared over chat, so it should be rotated in the
  MSG91 dashboard before production.
- **Confirm which account the authkey belongs to.** On 2026-10-31 the client reported
  49 credits in the MSG91 dashboard while every balance endpoint answered `0` for this
  authkey. Either the credits sit in a different account (a sub-account, or a login
  other than the one that issued the key), or the legacy balance figure does not track
  the current plan. Worth settling before anyone builds on that number again.
- **Real send verified end to end** on 2026-10-30: DLT template
  `1777179329093572727` was approved that morning, the sender is `TETPVT`, and the
  code travels in the template variable `var1`. Silence before that date was the
  unapproved template, two swapped DLT identifiers, and the variable name — not the
  provider integration.
- **Email provider still undecided** — the remaining half of GAP-12.
