# Client decision — SMS provider is MSG91, received 2026-10-14

Resolves **GAP-12** (SMS provider undecided) from
`client-provider-decisions-2026-10-01.md`. The client supplied an MSG91 account and
confirmed MSG91 as the transactional SMS provider for one-time codes. This is the
authority for how OTPs are delivered; it does not change the email provider, which
remains open.

## Decision

- **Provider: MSG91.** OTPs are delivered through MSG91's **Flow API**
  (`POST https://control.msg91.com/api/v5/flow/`), authenticated with the account
  **authkey**.
- **SMS stays OTP-only.** The client's earlier answer G1 keeps SMS to one-time codes
  and nothing else, as a cost saving. The delivery seam reflects that: its only
  operation is `sendOtp`.
- **DLT registration remains the client's to complete.** It is required for
  transactional SMS in India regardless of provider.

## Why the Flow API and not MSG91's OTP API

MSG91 also offers a SendOTP API that generates and verifies the code itself. Using it
would move verification into the vendor while the platform already owns OTP state: codes
are hashed under `OTP_HASH_SECRET`, attempt-counted, and expired against `OtpRequest`,
and the delete-account flow consumes a code at a later step. Two sources of truth for
"is this code valid" is the exact ambiguity the OTP module was written to avoid, so the
code travels as a Flow template variable and MSG91 only delivers it.

## Effect on the build

- `SmsGateway` (abstract) with `Msg91SmsGateway` implementation and a small
  `SmsModule`, bound like `PaymentGateway`/`RazorpayPaymentGateway` so tests can
  substitute a gateway without the network.- `AuthController.requestOtp` sends via the gateway. **Outside production**, when
  the gateway is unconfigured, the response echoes `dev_code` so the flow is testable
  without an account. **In production**, an unconfigured gateway fails closed with
  `401` rather than answering success for a code that was never sent.
- The gateway checks the account's **transactional balance before sending**
  (2026-10-30). MSG91 accepts a Flow request, answers `type: "success"` with a
  request id, and only afterwards drops the message when the wallet is empty — to us
  that is indistinguishable from a delivered code, and it is what hid an exhausted
  account for days. A confirmed zero now refuses the send and surfaces the reason;
  an unreachable balance probe does **not** block, so the guard cannot itself become
  a second reason codes go unsent. The reading is cached for a minute, so a burst of
  logins costs one probe rather than one per code.
- That refusal is now **named**, so the app can say something useful (2026-10-31). In
  production it answers `503` with `code: "SMS_UNAVAILABLE"` and copy written for a
  user ("we could not text your code just now") — the vendor diagnostic stays in the
  log, where an operator can act on it. In development the code is still echoed as
  `dev_code`, but alongside a `delivery_warning` so an echoed code cannot pass for a
  delivered SMS; that blind spot is what kept an empty wallet invisible. Every other
  send failure is untouched and still surfaces as-is.

- New configuration: `SMS_TEMPLATE_ID` (the MSG91 template id, distinct from the DLT
  template id), `SMS_OTP_TEMPLATE_VAR` (the template variable that holds the code,
  default `OTP`), and `SMS_COUNTRY_CODE` (default `91`). `SMS_PROVIDER_API_KEY` holds
  the authkey; `SMS_DLT_*` stay for compliance.
