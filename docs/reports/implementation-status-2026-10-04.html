1. Executive summary

The API is functionally complete through Phase 3 (Discovery). A user can register and sign in, hold a profile with photos and master-data attributes, and browse other users through a two-way net-worth visibility preference instead of the earlier same-category partition. Every phase was verified against a real PostgreSQL 16 instance, not only against unit-test doubles.

The most recent delivery replaced hard same-category discovery with two independently editable preferences. This is the single largest behavioural change in the project so far, and it changed a pricing rule: with cross-band discovery possible, the unlock price must come from the target's category rather than the viewer's, so the amount is knowable before checkout.

Three defects that were invisible to unit tests surfaced during live verification and are now fixed and covered — details in section 8. All 390 tests pass and the full npm run verify pipeline (Prisma validation and generation, typecheck, lint, test, build) exits clean.

4. Features implemented in this cycle

4.1 Two-way net-worth visibility and discoverability

The prior rule was that a user only ever saw profiles in their own net-worth band. That is replaced by two independent, user-editable lists:

  • discover — the bands this user wants to browse.
  • visible_to — the bands allowed to browse this user.

A candidate is returned only when both hold:

  1. the candidate's band appears in the viewer's effective discover list, and
  2. the viewer's band appears in the candidate's effective visible_to list.

Cross-band discovery is therefore opt-in on both sides and cannot happen by accident. Verified over HTTP: withdrawing either side's opt-in immediately removes the profile from the feed, and a band that nobody accepts is not even reported as searched.

4.2 Category options endpoint

GET /master-data/net-worth-categories serves the four active bands in display order with their bounds as strings, because the values exceed the safe integer range in JavaScript. PENDING_REVIEW is returned but flagged is_discoverable: false, which is a property of the band rather than a per-user permission. Each band carries its setup-fee quote.

Setup fee confirmed: ₹15.00 base plus 18% GST = ₹17.70 payable.

GAP-5 resolved 2026-10-03. GST is added on top, not included. One per account lifetime, collected only after ID verification, recorded under a distinct payment purpose so it can never be confused with a contact unlock.

4.3 Locked discovery cards

  • Exactly four keys per card: profile_id, photos, profile_locked, unlock_price.
  • Built by explicit projection, never an object spread, so the hidden-field rule is enforced by the shape of the response rather than by code review.
  • No name, contact, income, religion, community, horoscope or object key is exposed. Asserted by scanning the whole serialized payload, not just the documented fields.
  • Unlock price derived from the target's category, so it is known before checkout. Verified: a cross-band card quoted 499.00 + GST = 588.82 while the same feed's own-band card quoted 249.00 + GST = 293.82.
  • Only APPROVED photos are exposed, through per-request presigned URLs.

4.4 Eligibility and safety gates applied to the read path

A candidate must be an approved, active, non-deleted profile belonging to a user who is active, ID-verified, setup-fee paid, not anonymised, and not blocked with the viewer in either direction. Both block directions are expressed as none relations rather than joins, so a duplicate row cannot resurface a blocked user through the join.

6. Business rules settled at implementation time

The specification was silent on three points. Each was decided explicitly and recorded in docs/decisions/visibility-discoverability-2026-10-03.md rather than inferred at runtime.

QuestionDecision and rationale
What does an unset list mean?The user's own band only. Behaviour is identical to the old partition until the user opts in, so nobody is silently exposed to a band they never chose.
What does an empty list mean?Nobody, validly. It doubles as a pause control, which is why explicit configured flags are required rather than inferring intent from an empty table.
Can a request widen scope?No. A per-request category is rejected by the contract. This is why GET /me/visibility returns raw stored lists plus flags instead of fabricating the default into the response.

7. Defects found and fixed

Each of the three was unreachable from unit tests and was caught by running against real PostgreSQL. All three now have regression coverage.

7.1 Foreign Decimal instances threw on every priced response

Fixed toDecimal tested instanceof Decimal. Prisma's driver adapter constructs Decimals from its own bundled copy of decimal.js, so the check fails for any value read from the database. Such a value fell through to value.trim() and threw value.trim is not a function, producing a 500 on every endpoint that returns money. Now duck-typed, with toFixed rather than toString so a copy configured for exponent notation still parses. The saved preference body deliberately keeps strict types, because there a wrongly typed value is a client bug worth surfacing.

7.2 Every paginated request was rejected

Fixed Query parameters arrive as strings, so ?limit=1 failed a plain z.number() with "Expected number, received string". Pagination was unusable over HTTP while passing in unit tests, which construct typed objects directly. Numeric and boolean query fields now coerce, with one deliberate exception: use_saved_preference does not use z.coerce.boolean(), because that maps every non-empty string to true and would invert an explicit false.

7.3 The response claimed a preference had been ignored when it had not

Fixed preference_applied echoed the request flag, while the scope was in fact always computed from the saved preference. Sending use_saved_preference=false produced a response claiming preferences were skipped on cards that preferences had filtered. Now always true, with the flag documented as compatibility-only, since honouring it would reintroduce the scope-widening bypass.

7.4 Two false alarms worth recording

Both looked like product bugs and were faults in the test fixtures:

  • Cursor pagination appeared broken. The seeded profile IDs were 19 characters while the cursor validator requires 20–32, as real cuids are 25. Rejected IDs silently reset pagination to page 1. The validator was correct; the fixture was unrealistic. Fixtures now generate cuid-shaped IDs.
  • The never-saved default appeared missing. GET /me/visibility correctly returns empty lists for an unsaved account, with the flags false and the own category reported alongside. The own-band default is applied when the preference is resolved for a search, not written back as though the user had chosen it.

9.3 Environment and tooling limits

  • Live object storage untested. The configured MinIO image is unavailable, so a real PUT has not been exercised. Presigned URL generation itself is verified.
  • Missing provider credentials: Razorpay, Cashfree, Firebase, domain, SMS/email, DLT. All external; none block Phases 1–3.
  • API test suite memory ceiling. With roughly 2.6 GB free RAM the API suite intermittently exhausts the Node heap when Jest runs its default worker count. It passes reliably with --maxWorkers=2. This is a constraint of the development machine, not a code defect, so the repository default has not been changed — flagging it for a decision.
