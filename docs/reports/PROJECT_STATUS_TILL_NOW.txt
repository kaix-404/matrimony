RECENT ACCOMPLISHMENTS

Client Feedback Round (items 1-4)

  - Sign-in persistence: a member stays signed in for 30 days. The refresh token
    carries the long lifetime, the access token refreshes transparently on the first
    401, and expo-secure-store keeps the pair across restarts, so the app opens on the
    signed-in screen.
  - Registration in the client's order: mobile plus OTP, then the net-worth band, then
    profile setup, then review, then identity verification, then the one-time setup
    fee. The API enforces the same sequence through UserStatus.
  - Settings, and only what was asked for: partner preferences, discovery and
    visibility filters, blocked members, data export/deletion requests, change mobile
    number, identity verification, delete account, pricing and help. Pause/resume is
    the profile screen's visibility toggle, the same control the API exposes.
  - Partner preferences from the client's lists: religion, sub-caste, education and
    profession are picked, not typed. Sub-castes are offered only for the preferred
    religion, and changing religion clears a sub-caste that no longer applies.
    Education and profession preferences reference the same list ids a profile uses.

Email Address Change (MSG91 Email)

  - Settings now offers "Add or change email"; the address is verified by a code
    sent to it, so a typo cannot silently put account mail somewhere unreachable.
  - The code is bound to the mailbox it was issued for and carries its own OTP
    purpose, so it is never redeemable as a sign-in or as a number change.
  - No sessions are revoked: email is not a login identity, and losing a mailbox
    must not sign a member out of the app.
  - Delivery goes through MSG91's email API behind an EmailGateway seam, mirroring
    SMS; unconfigured, it fails closed with EMAIL_UNAVAILABLE rather than claiming
    a send. The deployment still needs EMAIL_PROVIDER_API_KEY, EMAIL_FROM_ADDRESS
    and EMAIL_TEMPLATE_ID.

Master List Console (Admin)

  - The lists members pick from were read-only outside the seed, so a missing option
    needed a code change and a release. The console now lists every value, including
    retired ones, and can add, rename and retire them (page /master-lists,
    GET /admin/master-lists, POST /admin/master-lists/:key/values,
    POST /admin/master-lists/values/:id).
  - Nothing is deleted: profiles reference these rows by id and sub-castes by text, so
    retiring removes a value from the pickers while keeping it on every profile that
    already chose it. Renaming is how a spelling is corrected, and it reaches every
    profile at once.
  - Structure is read from the data: a list with sections requires one, a flat list
    refuses one, and a sub-caste can only be filed under a religion that already
    exists. A section typed with different capitalisation is matched to the existing
    one.
  - Every change is audited with the value before and after; master_data:read and
    master_data:write keep viewing separate from changing.

Client Datapoints, End to End

  - All six supplied lists are seeded and live: religion 13, mother tongue 64,
    education 95 in 17 sections, occupation 140 in 24 sections, sub-caste 835 across
    the religion blocks plus a shared "Other Sub Cast" section, and states 36.
  - A parity test reads docs/Data Points list/ and compares it with the seeded arrays:
    every value, its section, and the religion block each sub-caste came from. It
    caught "Designer", which the client lists under both Engineering and Media &
    Entertainment and the transcription had collapsed into one.
  - Community is wired but empty because no community list was supplied; the picker
    stays hidden while the list has no values rather than opening a sheet whose only
    row is "Not set".

Partner Preference Fixes

  - The preference read and write paths selected country/state/city instead of
    preferredCountry/preferredState/preferredCity, so every preference GET/PUT and
    every discovery search failed with a 500 for signed-in members. The selects are
    now typed against Prisma's own field list, with a guard test.
  - Education and profession preferences were added as list references
    (education_id / profession_id) with a migration, pickers in a dedicated
    "Education and career" section, and discovery predicates.

Biodata Import (Member App + API)

  - A member uploads a biodata (typed PDF or plain text) and has the recognised fields
    proposed for the profile form instead of retyping them.
  - Extraction is a deterministic server-side text parser (no OCR/LLM provider is
    configured), so the client ships no parser; the PDF path uses node:zlib alone.
  - Same three-step upload shape as photos: presigned PUT, direct upload, then the
    object key is posted to POST /profile/biodata/parse. The API accepts only a key
    under the caller's own biodata/ prefix; the response is a proposal, never a save.

Phase 9 - Member App (Expo + React Native)

  - apps/mobile: Expo SDK 57, React Native 0.86, Expo Router, strict TypeScript,
    consuming @matrimony/shared contracts; the typed API client validates every
    request and response with Zod.
  - Discovery: cursor-paginated feed of locked cards, temporary filters and sort, and a
    filter/sort bottom sheet.
  - Previews and payments: locked/unlocked/expired states, Razorpay checkout in a
    WebView, status polling, and unlock expiry shown in the matches tab.
  - Account setup fee: verified accounts move to AWAITING_SETUP_FEE and the feed gates
    until payment, with the Rs 15.00 + 18% GST = Rs 17.70 breakdown.
  - Profile: completeness, field editing from the client's datapoints, direct-to-
    storage photo upload, biodata import, visibility toggle.
  - For You: interest picker, recommendation cards ranked by shared interests, and a
    flag-off state.

PLATFORM WORK (sections 15, 21, 30, 42, admin)

  - Unlock pre-expiry reminder: one PUSH notification about two hours before expiry,
    claimed by a conditional update so a restart cannot notify twice.
  - Firebase push: FCM HTTP v1 with a service-account assertion on node:crypto, no
    firebase-admin; dead tokens pruned; a 60-second dispatch sweep.
  - SMS OTP over MSG91 Flow API with an SmsGateway seam; fails closed when
    unconfigured and echoes dev_code outside production. 9 gateway tests.
  - Admin MFA: RFC 6238 TOTP, AES-256-GCM secret at rest, MFA challenge at login,
    audited reset.
  - Account retention purge: purgeAfter is read by a sweeper that anonymises the
    account, tombstones the mobile so the number can register again, and keeps payment
    records.
  - Report moderation: queue, detail, review, audited report:review rows.
  - Admin dashboard: Next.js 16, httpOnly cookie sessions with an edge proxy, pages for
    overview, moderation, profile review, photo review, identity checks, data
    requests, members, pricing, master lists and administrators.
